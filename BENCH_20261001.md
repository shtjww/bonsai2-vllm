## Kernel v2 experiment (2026-10-01, same day) — negative result, kept for the record

Hypothesis: v1's GEMV-per-token re-reads weights T times; a BLOCK_T batched kernel
(`ptq1_gemm_v2_kernel`) cuts DRAM traffic by BLOCK_T× and should win at bs≥16.

Micro-bench (same tensor looped 100×, 5120×17408, rel_err 4e-7 ✓):
- v2 best @T=32 (BT=16/BO=256/SK=8): 0.27 ms vs v1 0.39 ms — **v2 +44%**

End-to-end (full model, vLLM serving, this same protocol):

| bs | v1 | v2 | verdict |
|---|---|---|---|
| 8 | 204.4 | 201.9 | ~tie |
| 16 | **226.0** | 126.0 | **v2 −44%** |
| 32 | **233.9** | 226.2 | v2 −3% |

**Why the flip:** the micro-bench loops one tensor so its weights stay L2-resident —
exactly the regime where v2's traffic reduction is worthless. v1's real strength is
that T concurrent token programs re-reading the same ~20MB layer hit L2 at ~1.6 TB/s
effective; v2 is compute-bound (~250 GB/s effective) because the fused trit-decode
FMA path doesn't use tensor cores. The fork's 372.8 tok/s @bs=32 ≈ 3.1 TB/s
equivalent — only reachable with a tl.dot/tensor-core GEMM (v3 candidate), not with
traffic tricks.

v2 code kept in `vllm_bonsai/ternary_kernel.py`, gated behind `BONSAI_KERNEL_V2=1`
(default off; production path is v1 for T<16).

## Kernel v3 (tensor core) — 2026-10-01 — SUCCESS, now the default for T>=16

Root-cause reasoning: the fork's 372.8 tok/s @bs=32 ≈ 3.1 TB/s equivalent bandwidth —
impossible over a 1.4 TB/s DRAM link unless the matmul runs on tensor cores. So v3
moves the MMA there: each program decodes a full 128-weight PTQ1_0 block into a
(128, BLOCK_OUT) fp16 tile with vectorized index math (CUDA cores), then
`tl.dot(x_tile, w_tile)` (tensor cores). Decode and MMA overlap on different units.

Kernel bench (honest methodology: cycle 8 distinct ffn_down layers, 160MB working
set busts L2; winner config BT=16/BO=64/SK=8/NW=4/NS=1):

| T | v1 | v3 | speedup |
|---|---|---|---|
| 16 | 0.209 ms/tensor | 0.043 ms/tensor | 4.9x |
| 32 | 0.591 ms/tensor | 0.074 ms/tensor | 8.0x |

End-to-end (vLLM serving, this same protocol, fork at `-np 32`):

| bs | v1 | fork -np32 | **v3** | v3 vs fork |
|---|---|---|---|---|
| 16 | 226.4 | 299.4 | **761.9** | **2.5x** |
| 32 | 234.0 | 372.8 | **862.4** | **2.3x** |

Correctness: rel_err 1.8e-4 (x cast to fp16 for MMA). 16-way greedy check vs
single-stream: 14/16 outputs byte-identical, 2/16 diverged after ~80% of tokens
(batch-dependent numerics, same class as stock vLLM fp16 serving).
T=1 path unchanged (v1 GEMV), so the 98.94% parity claim stands as-is.
Config: BT=16/BO=64/SK=8/num_warps=4/num_stages=1; `BONSAI_KERNEL_V3=0` reverts to v1.
